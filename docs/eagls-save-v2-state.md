# EAGLS v2.0部分状态字段与验证方法

适用范围：EAGLS v2.0；profile：`eagls-v2.0-pe1.5.0.0`。版本、容器及字体迁移根因见[格式指南](eagls-save-v2.md)。以下偏移均指解压后的块0，数值按小端读取。此文不代表所有状态字段均已解释，也不是通用EAGLS编辑规范。

## 只读状态报告

```
eagls save state Save30.sav --out Save30.json
eagls save state GlobalSave.sav --kind global --out GlobalSave.json
```

JSON格式为 `eagls-v2-state-report-v1`，明确标记 `partial_schema: true`。`symbols` 只列登记字节为1的槽；每项含槽号、记录偏移及类型。数值项含100个有符号i32和数据偏移；字符串项仅含标识与长度，不导出正文。ASCII标识用 `name`，其他标识按原始字节导出 `name_bytes_hex`，不猜测编码。

普通存档还输出八个u16的 Windows SYSTEMTIME（年、月、星期、日、时、分、秒、毫秒）及五个执行上下文的登记字节/当前与保存游标。游标是脚本缓冲区的**字节位置**，不是文本行号（解释器0x421651、0x421657）。上下文基址 `0x12DF8C`，步长 `0x4E94`；+4当前游标，+0x1008保存游标。其余栈字段未完全解析。

GlobalSave报告另含32个原始设置字和11个具名性能校准值，见下表。报告不会修改存档、查找游戏或启动进程；同文件输出即使指定 `--overwrite` 也拒绝。

### 执行上下文中的调用栈与块控制

上下文内偏移（不同于整个块的偏移）：

| 偏移 | 部分含义 | 证据 |
| --- | --- | --- |
| `+0x104C` | 脚本调用深度 | 0x4272E8读取后选择调用帧，0x42747C递增，返回路径递减后恢复 |
| `+0x1050` | 16个条件链分支已执行标志i32，按嵌套深度索引 | 条件起始120写0/1；else 121与else-if 122检查同链是否已执行分支，见下文 |
| `+0x1090` | 16个块跳转游标i32，-1为无跳转哨兵 | 0x4216D2读取，非-1时写回解释器当前游标 |
| `+0x10D0` | 当前块嵌套深度 | 0x4216A9递减、0x421770递增、0x421777与16比较 |
| `+0x10D4` | 16个调用帧，步长`0x3DC` | 调用0x4272E8～0x42747C，返回0x427510～0x4276E5；数组终点恰为上下文步长`0x4E94` |

调用帧内+0为返回字节游标，+4起复制调用者脚本名，+0x354保存16个块标志，+0x394保存块深度，+0x398保存16个块跳转游标。其他区域仍不解释。报告不导出脚本名或未知区，仅导出这些数值；调用深度大于16时标记`call_depth_valid: false`且不遍历帧，避免越界。未启用上下文仍可能有陈旧数组，不能把所有槽当成正在运行的线程。

条件链处理器120（0x42AA2D）在条件为假时于0x42AA8A写0并跳过配对花括号，为真时于0x42ABC3写1；两路均将跳转游标重置为-1。121（0x42AC66）在0x42AC96检查同一深度的标志，已为1就跳过else体，否则于0x42ADA6写1后进入。122（0x42ADCB）先求值，只有条件为真且该链尚未执行分支时，才于0x42AE3B写1并进入else-if体。因此这组标志属于解释器条件链状态，不能作为人物或剧情完成标记。

这些是静态控制流程与真实存档交叉核对的结果，尚未用修改返回游标的方式做游戏内跳转测试。条件链分类没有完整解释循环、表达式求值、块解析器或调用帧未知区域；`partial_schema`仍为true。

## 符号表

| 块0 | 数值表 | 槽数/步长 | 字符串表 | 槽数/步长 |
| --- | --- | --- | --- | --- |
| 普通 | `0x18` | 997 / `0x1D4` | `0x71EC0` | 97 / `0x140` |
| GlobalSave | `0x4CC` | 997 / `0x1D4` | `0x72374` | 97 / `0x140` |

槽+0为登记字节，+1起64字节为标识。数值+0x44起为100个i32；字符串+0x41起为255字节。槽为散列/探测布局，存在空洞，不能按创建顺序定位，也不能把某个样本中的槽地址推广到任意存档。应按标识查找后再计算元素位置。

结构证据：本地查找0x4311F5～0x431235，全局查找0x431299～0x43134D，数值/字符串删除0x430FE4～0x430FF6、0x43110B～0x43111D，插入/查询0x42F290、0x42F370。

### 局部变量的哈希元数据

普通块0的`0x71EBC`与`0x79800`分别保存数值/字符串表的**最大探测次数**，不是活跃条目数。插入0x42F358～0x42F360更新历史最大值；查找0x42F47B～0x42F486以该值为界。报告在`local_symbol_lookup`中原样列出。历史最大值可以大于当前仍在用的最大次数；例如Save30字符串上限4，但现存变量最多用到3次。

已在五份真实存档、每份164或165个局部符号上复现槽位。对于本次样本的ASCII小写标识，容量m（997或97），算法为：

```
H = fold(name, h=0, h=(96*h + signed_byte - 32) rem m)
G = fold(name, h=0, h=(118*h + signed_byte - 19) rem m)
previous = 0
for probe = 1 .. saved_max_probe:
    slot = ((H + previous + probe) * probe) rem m
    if record[slot] is live and name matches: found
    if slot == 0: previous = 1
    else:
        previous = G
        if slot == G: previous = (G + signed_first_byte) rem m
```

`rem`为x86有符号余数，哈希运算按32位整数行为；不是Python对负数的默认模运算。`@`全局变量在此版本走线性扫描，不强行套用该局部表算法。新增/改名变量时，既要正确放槽，也要维护最大探测次数；只设置登记字节和名字可能导致报告扫描可见、游戏查找失败。本工具仍只读报告，不提供未经验证的变量插入器。

## 游戏进度

- `_day[0]`：游戏天数，与保存文件日期不同。样本第90格=1，第20格=7，第31格=21；这些样本中元素地址为 `0x10D0`。
- `_systemccs`：手机复合状态数组；照片为11～22、31～42、51～62、71～82四组，各12张。其余元素不能整体当作照片布尔值。手机读取证据0x43ED62～0x43EDC2及剧情控制语句对应写入。第31格（Save30）标记计数 **2、0、12、0**；用户确认顺序为角色1、角色2、角色3、角色4。**标记数量与手机可见计数须分开**：只改四个照片标记后的存档数值为3、1、11、1，用户实际看到3、0、11、0；再保存83格后仍保留3、1、11、1。第三组首张由已解锁变为未解锁，用户确认是角色3的第一张。

相册入口另有 `_systemccs[4～7]` 四个标记。0x43E22C构造`4+i`索引，0x43E285读取，非零才计入可切换相册；Save30四个值为1、0、1、0，与缺失的第二/四组一致。仅开启第二/四入口后，桌面四人图标出现，但进入第四组报CG读取失败，不能宣称全界面通过。

还须维护 `_systemccs[10/30/50/70]` 中的初始照片索引。0x43E2D3～0x43E31B读取各组前一格，再据此计算相册初始选择；原第二/四组值为0。正常脚本同处写入三类字段，例如sc_b01写30=31、5=1，sc_d01写70=71、7=1，同时登记相应照片位。基于同一存档补齐入口和索引31/71后，用户确认四组**3、1、11、1**，进入、切换、返回、保存76、重读及退出均正常。独立解码76确认入口全1、初始索引12/31/62/71和照片标记数量保留，22份原编号存档哈希均未变。

因此编辑照片不能只改计数或入口。`state`额外按变量名导出`phone_albums`：入口、照片位计数、初始索引及其是否在组内/对应照片位是否解锁；`inconsistent_entry_state`只标记入口开启而索引越界，不会自动改档，也不声称检测所有相册状态问题。
- `_advance`：路线/事件推进数组，完整含义未解析。
- `_place`：地图目标状态数组。第11→12格（Save10→Save11）`[40]` 从2变1，两个样本中元素偏移 `0x5253C`。初始化控制脚本 `00LReg_Manager` 写2，`sc_g14` 写1，`MAP12`检查0/1并调用该事件。用户确认目标是电车内地图中央的OL女性；同一份Save11仅改该值的三份副本在游戏内确认：**1不可选，2可选且可进入剧情，0目标仍在但瞄准框消失**，天数和脚本位置保持相同。两份原档另有天数4→5等差异，不能称为原档只差一处的实验。日期推进后同场景可能出现新目标，不能把全部元素当成互不相关的角色永久布尔标记。

静态事件脚本→`_place`索引：g01→15、g02→34、g03→15、g04→36、g05→39、g06→17、g07→14、g08→10、g09→20、g10→8、g11→22、g12→21、g13→24、g14→40、g15→44、g16→41、g17→42、g18→43、g19→23。只确认这些脚本写1；g01/g03共用索引，不据此推断19个独立角色，也未给g20虚构同类标记。

### 全局收藏解锁看登记状态

CG、动画、场景分别使用 `@<资源名>`、`@mov_<资源名>`、`@reco_<脚本名>` 的符号存在性，**不是数值非零**。`00CGFlag` / `00RecoFlag`先检查存在，不存在才登记；0x431140返回存在状态。真实已解锁变量的100个数值通常全部为0。

两份原安装/旧备份的GlobalSave与当前全开版本对比：仅新增 `@g20`、`@g20r1`、`@g20r2`、`@g20r3`、`@reco_sc_g20` 五个符号，没有删除符号，共有变量数值也没有变化。符合最后一组CG及场景解锁；不能把单个 `@collect` 宣称为全解锁开关。

## 已读记录独立于收藏登记

GlobalSave块0偏移`0xF2928`为100000（`0x186A0`）字节的已读表，内存VA`0xD74AD8`。它是逐消息编号的字节数组，不是打包位图，也不是全局符号存在性表。原版脚本语法`&<编号>"<正文>"`含24057个唯一编号，恰好覆盖0～24056；此数量是消息标记数，不是场景数。不同游戏/profile的编号和偏移必须重新核对。

解释器`&`分派到0x421F57，提取引号前编号；0x422415～0x422425将其转为整数并查表，值**恰为1**才进入已读颜色和自动跳过分支；0x422B39～0x422B4C对同一编号写1。0x4204B0～0x4204BC初始化清零100000字节。该表位于GlobalSave序列化范围内，与用户观察的新游戏仍保留已读状态一致。

报告`read_history`只输出偏移、容量、`read_value:1`、零/1/其他字节数量，不导出正文，不把其他非零值擅自当已读，不将余下容量中的零称为尚未阅读的有效消息。三份真实GlobalSave的C++结果与独立Python解码逐项一致；边界测试覆盖首尾、相邻非表字节、2/255异常值以及只读性。尚未改写已读表做游戏内验收。

## 引擎内置控制字与脚本变量分开

下列冒号标识直接解析为固定地址，不经普通局部/全局符号表。普通存档报告`engine_controls`保留其名称、偏移和有符号原始值，不归一化为布尔值，也不把所有名含Flg的状态当作剧情解锁。

| 内置标识 | 普通块0偏移 | getter VA |
| --- | --- | --- |
| `:SkipFlg` | `0x157290` | `0x42FCCD` |
| `:AutoFlg` | `0x157298` | `0x42FD31` |
| `:SuperSkipFlg` | `0x15729C` | `0x42FC69` |
| `:SceneFlg` | `0x1572A0` | `0x42FD99` |
| `:RightClickFlg` | `0x1572A8` | `0x42FEE9` |

`:SkipFlg`和`:AutoFlg`的赋值路径另见0x431D20/0x431D90。这些值在文件中存在，不代表加载后原值全部继续生效：0x4201B0～0x4201BC将`0x157290/294/298`重置为0/1/0，中间字的业务语义仍未知。`:SceneFlg`仅按引擎名称报告，不能等同于场景鉴赏收藏登记。

反例`:QuickSaveFlg` getter0x42FE69读取运行时字节`0x103D9A4`，位于两类保存块范围之外。不能根据同属内置flag就虚构存档偏移。这里的映射是本profile静态证据，未对各字逐项改档测试。另在同一真实进程，由用户关闭→开启→关闭自动播放，三次只读采集`:AutoFlg`为0→1→0，其他五个采集字保持不变；只确认自动按钮对应，不外推所有生命周期。

输入生命周期另有实证限制：用户确认开启自动时点击任意位置会结束自动，无法按提出的操作步骤保留自动状态进入读档菜单。静态消息分派也确认`WM_LBUTTONDOWN(0x201)`→0x455DE9（0x455DFD/0x455E02清Skip/Auto）、`WM_RBUTTONDOWN(0x204)`→0x455F14（0x455F21/0x455F27清Skip/Auto）。因此不能把进入读档前后的0归因于“加载才重置”；恢复函数的清零证据与UI操作观测分别记录，不强造不可达对照。

## 音频及辅助快照的分类边界

命令100检查声道0～6；0/1走音乐音量、2～5走音效、6走语音。资源名起点`0x146870`步长`0x40`，模式字节`0x146A70+i`，第四实参保存于`0x146A98+4*i`，含义/单位仍保留原始值。读档0x41FF80～0x42007B先停止7路，仅在总声音启用且保存模式为2或7时重新启动0～5路，不能把它概括成只有6个活动声道或所有保存声音均重播。

辅助第二块仍需原样保留。命令75(1)及72的部分路径可复制完整状态到辅助快照，UI动作13在开关有效时可恢复；但开启调用仅见预留00Select脚本，用户确认本作未使用该菜单。初始化实际还有两处75(0)关闭开关。28份当前编号档（含测试副本）第二块均为零；这不证明其他游戏无用途，也不强造本作菜单测试。

研究范围以状态类别和存储机制为准：脚本自定义变量、全局收藏、全局已读、设置、引擎控制、对象/音频及快照。不穷举本作所有支线索引；未知对象字段仍保留，`partial_schema`继续为true。

### 手动性能校准

入口为设置第四页右下的“手动重新设置性能”，对话框140；其11个输入框ID1119～1129。0x452B1A～0x452B97从持久字段填充临时数组，0x452BE6～0x452C94在退出小窗口时读输入、写回持久字段。手动窗口把<=0归一化为1。参数单位是引擎性能校准值，不能仅凭Time后缀称为毫秒。

## 实际加载验证的边界

在目标游戏r49修复环境完成两轮用户操作验证，全程使用空槽副本，原有编号存档哈希未变：

1. 第90格状态使用 `--store` 重新编码到第84格；加载、切换字体并推进一句、保存85、重读、返回和退出通过。独立解码确认重新编码的两个块与原状态完全相等。
2. 基于第85格，只修改保存SYSTEMTIME为2001/02/03及全部30个字体对象+0xA0为128，再编码到第86格。日期显示正确；加载、推进、保存87、重读和退出通过。解码87确认30个边缘alpha全部仍为128，保存时间自然更新。

字体从下一句才生效，故两次再保存的剧情游标有意前进。+0xA0是字形边缘alpha，+0xA4为描边分支开关，+0xA8为描边alpha乘数；不是RGB颜色（绘制0x409535、0x409633～648、0x4097A7～7C0）。验证未覆盖任意进度修改、未修复ISO程序或其他EAGLS版本。

相册测试另验证了照片位、独立入口及有效初始索引的组合；保留“只开入口时读取失败”的负例，避免将不完整状态作为编辑范例。

CTest覆盖状态报告的有符号数、零值收藏登记、空洞/失效槽、正文省略、固定块长度与输出保护；另外五个真实样本的全部符号报告与独立Python解码逐项相同。部分结构的静态字段证据见[机器可读证据](eagls-save-v2-evidence.json)。容器与语义的验证是两层，语义仍保持部分解析标记。

## 绘制记录的两类启用字节

此前以`0xA7500`作为图像字段基址列出的步长`0x14C`记录，外层基址为`0xA74FC`。计数VA`0x681D78`由`MaxCharLayer`读取（0x42E53B～0x42E560，键名VA0x484FA4），不能推广为所有图层计数。

外层`+0`（块偏移`0xA74FC+i*0x14C`）在渲染0x4335E6比较1；命令156在0x42D76E设1，命令158在0x42D9A0清0。另一个外层`+0x2C`（块偏移`0xA7528+i*0x14C`）由恢复0x41FE00比较1，决定是否重建图像；资源设置路径0x42CBEE/0x42D2C5设1，0x42D969清0。图像索引u16在外层`+4`。因此“参与渲染”和“载入时需要重建”是两个独立状态字节，不把二者混成单一剧情flag。

这仍是引擎静态结构分类；`MaxCharLayer`是配置名，不证明每项均为人物立绘，也未证明本作实际启用这一子系统。没有改动或查看图像内容，主/子图层等其他对象结构仍部分未知。
